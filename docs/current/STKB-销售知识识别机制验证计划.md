# STKB 销售知识识别机制验证计划

> 状态：规则包 v0.3 已接入并可页面审阅，等待真实模型重新验证分类与聚合效果
>
> 更新日期：2026-08-26
>
> 对应流程节点：`DocumentPackage → 销售知识识别 → 候选知识`

## 1. 验证目标

本轮验证销售知识识别节点能否以一份可用 `DocumentPackage` 为输入，通过后端真实调用大模型，形成经过程序校验、可回到来源证据、按业务对象边界聚合的候选知识。

本轮不验证 PDF、Office 等文件解析能力。药享保 PDF 由 Codex 代替解析能力生成全文 Markdown、页码锚点和质量说明；该结果必须标记为 `agent_assisted`，不能据此声称文件解析机制已经跑通。

本轮也不执行业务实体归一、跨资料知识归并、正式知识形成、向量投影或知识图谱投影。候选知识不获得稳定 `KnowledgeObject` 身份。

## 2. 核心问题

1. 模型是否默认对整份全文进行一次综合识别，而不是按 D1—D5 或22个知识内容模块循环调用？
2. 一次识别能否输出跨域、跨模块的多个候选知识？
3. 候选是否按业务对象聚合，而不是按句子、字段或表格单元格机械拆分？
4. 候选的分类、实体提及、引用角色建议和关系建议是否都能回到 `DocumentPackage` 的有效证据锚点？
5. 模型输出不符合合同或引用无效证据时，程序能否拒绝结果并明确定位错误？
6. 同一模型配置重复运行时，关键候选是否具有可接受的稳定性？

## 3. 输入合同

本轮输入是一份状态为 `available` 的 `DocumentPackage`，至少包含：

- 文档包 ID、工作区 ID 和来源文件名；
- 原件定位与 SHA-256；
- 一份可从头到尾阅读的 `full.md` 及 SHA-256；
- 可解析的页码级来源锚点；
- 代理解析方式和已知质量问题。

首个真实样例使用《药享保互联网问诊险产品培训》PPTX 的代理解析全文。原件和运行结果保留在本地 `workspace/`，不提交内部原始资料。

## 4. 真实模型调用机制

后端必须真实调用配置的模型服务，首个适配器使用 OpenAI-compatible Chat Completions 协议。模型地址、模型名、API Key 环境变量名、温度、超时、最大输出量、重试次数和分段阈值统一从配置读取。

默认执行顺序：

```text
读取 DocumentPackage
→ 组装 D1—D5/22模块版本化规则包、候选合同和证据锚点规则
→ 判断整份调用或按 Markdown 结构临时分段
→ 调用真实模型并要求 JSON 输出
→ 解析顶层响应
→ 逐候选进行 Pydantic 与业务合同校验
→ 校验证据锚点
→ 文档内聚合重复候选
→ 形成覆盖报告、异常和运行指标
```

网络错误、限流和超时允许按配置重试。JSON 结构错误允许执行一次显式修复调用；语义错误不得由程序静默补全。每次调用、重试和修复都必须进入运行轨迹。

模型将 `domain` 重复写成合法模块码时，程序可依据已发布目录执行确定性上级域规范化，但必须同时保留候选 ID、原值、规范值和原因；其他分类或对象类型错误仍按合同拒绝。最终调用失败也形成 `failed` 运行并写入完整失败轨迹。

### 4.1 销售知识模型规则包及传递方式

当前运行时规则包为 `d1-d5-v0.3`，状态为 `sample_validation`。规则来源是 [STKB D1—D5 知识对象与业务图模型映射矩阵](./STKB-D1-D5知识对象与业务图模型映射矩阵.md)，运行表达保存在 `services/app/features/sales_knowledge_identification/rules/d1-d5-v0.3.toml`。规则包使用版本化文件作为事实源，不写入 PostgreSQL；数据库只记录某次识别实际使用的规则版本和内容指纹。五个销售知识域分别登记业务问题、含义和排除边界；每个模块至少包含业务含义、允许对象类型、核心对象、对象边界与分类裁决、典型来源和明确消费方。调试台“规则审阅”视图直接读取与模型调用相同的规则包，避免维护第二套展示数据。

每次识别调用都将完整22模块规则包放入 `system` 消息，将 `DocumentPackage` 元数据、当前允许的证据锚点和 Markdown 内容放入 `user` 消息。未超过结构分段阈值时传递全文 Markdown；超过阈值且存在页级结构时，每个调用只传当前 Markdown 结构分段及该分段锚点，但仍携带完整22模块规则包。当前不先按关键词选择模块，也不拆成22路调用。

`v0.2` 首先解决“模型只看到模块名和对象类型、看不到业务边界”的缺口，并补充 D3.1 场景阶段、D3.2 通用技巧、D3.3 条件策略、D5.1 卖点检测之间的分类裁决提示。`v0.3` 在不改变22模块集合的前提下补齐 D1—D5 域级含义与边界，并开放规则审阅视图。它们尚未经过新的真实模型三轮验证，不能沿用 `v0.1` 的运行结果声称分类效果已经改善。

## 5. 候选知识合同

每项候选至少包含：

- 本次运行内唯一的 `candidateId`；
- 一个主域、一个主模块和一个对象类型；
- 非空的类型化 `content`；
- 0～N 个实体提及及建议实体类型、引用角色和来源锚点；
- 1～N 个来源证据锚点；
- 0～N 个待判定实体关系或对象关系建议。

模型可以另外输出弱线索和无法判断项。程序依据有效候选、弱线索和异常生成22模块覆盖矩阵；不要求模型为未命中的模块生成空候选。

候选默认只在运行内存或设置保留期的调试空间流转。PostgreSQL 长期记录运行身份、模型和规则版本、计数、耗时、错误摘要和结果状态，不把候选当作正式知识层。

## 6. 调试 API

本轮提供以下公共测试缝：

```text
GET  /api/sales-knowledge-identification/document-packages/{id}
GET  /api/sales-knowledge-identification/catalog
POST /api/sales-knowledge-identification/runs
GET  /api/sales-knowledge-identification/runs?documentPackageId={id}&limit=5
GET  /api/sales-knowledge-identification/runs/{run_id}
GET  /api/sales-knowledge-identification/evaluations/{document_package_id}
```

`POST /runs` 必须执行真实模型调用并返回运行结果。测试替身只用于网络错误、格式错误等确定性分支，不能作为真实效果验收依据。

调试台面向使用者时按项目内原始资料选择，不要求输入或记忆 `DocumentPackage ID`。后端仍用该 ID 绑定原件、代理解析后的全文 Markdown、证据锚点、识别运行和评估结果。当前验证样例的原始 PPTX 位于本地 `workspace/source-materials/DP-YXB-TRAINING-20260821/`，其路径和 SHA-256 由对应 `manifest.json` 登记；原件和运行数据不提交 Git。

## 8. 评估方式

Codex 独立阅读原始资料，形成不注入识别 Prompt 的评估清单，并在真实模型运行后评价：

- 关键销售知识召回；
- D1—D5 分类和对象类型；
- 对象粒度；
- 证据支持；
- 实体提及和引用角色建议；
- 关系建议；
- 无依据生成；
- 同配置重复运行稳定性。

代理评估不得修改模型原始输出。确需裁决时另记 `proxy_adjudication`，保留评估者、时间、依据和结论。

## 9. 最低通过标准

- 首个真实样例实际调用配置模型成功；
- 非超长全文不产生22模块线性调用；
- 一次识别可以覆盖多个域或模块；
- 所有通过候选的证据锚点解析成功率为100%；
- 无证据候选和非法分类不会进入有效候选；
- 同一配置运行3次，评估清单中的核心候选均稳定出现；
- 没有明显的句子级、字段级或单元格级机械拆分；
- 页面能看到输入、模型调用、中间处理、结果、耗时和错误；
- PostgreSQL 只新增运行与调试记录，正式知识文件、pgvector 和 Neo4j 数据增量均为0。

## 11. 本轮验证结论

2026-08-21 已用同一 `DocumentPackage`、`qwen-plus` 和当时的 `d1-d5-v0.1` 简略目录完成3次结构分段真实识别。三次均为3次模型调用、没有输出截断，覆盖产品版本、药品清单、购买边界、服务流程、风险控制、客户动因、高频问答、卖点和组合销售方案；所有有效候选均只能引用所属结构段的精确来源锚点。

本节点的“真实模型识别并形成候选”召回与证据机制阶段通过，但还不能进入正式知识形成。`v0.1` 运行中组合方案虽三次均被识别，分类却在 D3.1 场景、D3.3 策略和 D5.1 卖点之间漂移；跨分段同义候选也尚未聚合。2026-08-23 已接入包含详细业务边界的 `d1-d5-v0.2`，2026-08-26 升级为可独立审阅域和模块规则的 `d1-d5-v0.3`。下一轮必须使用同一真实样例重新运行并对比，之后才能判断分类裁决是否有效。完整代理评估和旧运行 ID 保留在本地 `workspace/evaluations/DP-YXB-TRAINING-20260821/validation-report.md`，不提交原始材料或运行数据。

实测边界：PostgreSQL 写入文档包和运行账本；正式知识 Markdown、pgvector 数据、Neo4j 节点与关系增量均为0。本结论不包含文件解析能力，也不代表候选已被人工确认或获得正式知识身份。
