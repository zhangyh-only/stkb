# STKB 方案讨论决策台账

> 状态：滚动讨论记录，非正式实现合同
>
> 最后更新：2026-08-20
>
> 用途：记录总体方案在架构收敛过程中的当前有效结论、待验证问题和已放弃方向，防止多轮讨论中丢失上下文或将旧表述误当成最新决定。

## 1. 使用规则

- 本台账不替代总体方案、领域词汇或后续实现合同。
- 本台账中的“已确认”表示后续讨论应默认遵循；“待样例验证”表示不得提前写成实现合同。
- 如本台账与当前总体方案讨论稿冲突，方案讨论期间先以本台账中日期更新的明确决定为准；真实样例验证后再统一回写总体方案。
- 方案逻辑闭环前不进入全量开发、生产数据库建模、字段冻结或中间件定型；对象、关系、存储和验收合同明确并通过评审后，才开展范围受控、验收标准明确的技术验证。

## 2. 当前有效基线

### 2.1 责任链与业务范围

- 当前责任链统一称为“资料接入与知识构建”，不再简称为“预处理”。
- 当前方案采用 D1 产品与事实、D2 客户与画像、D3 方法与策略、D4 语料与案例、D5 评估与基准五个销售知识域，以及现有 22 个知识内容模块（20 个计划建设、2 个可选）作为分类基线。
- 当前方案按既有职责梳理五个知识域和对应知识内容模块，不再讨论模块合并、拆分或重命名。架构需要支持知识域、知识内容模块、知识对象类型及其归属规则后续演进，不能把当前分类硬编码为永久结构。
- STKB 存放可复用销售知识；AI 应用提示词、运行配置、任务状态和实时会话状态与知识分离。
- STKB 采用“知识工作区”表达 SaaS 场景下的数据隔离和知识维护边界。资料从接入开始即属于某个工作区，后续解析、抽取、归并、发布及三种知识视图都不能丢失该边界。
- 当前以《STKB 资料接入与知识构建完整方案（讨论稿）》作为唯一连续方案入口；D1—D5 映射矩阵是业务模型附件，本台账只保存决定及其历史依据，不再分别维护第二份存储方案正文。

### 2.2 来源资料与知识抽取

- 一份来源资料对应一个 `DocumentPackage`。解析过程先保存原件并登记存储引用，再提取正文、表格和必要随文资源，随文资源落存后才组装引用它们的全文 Markdown；解析主交付是一份完整可读的全文 Markdown。
- 新接入的每份资料默认形成独立 `DocumentPackage`，不根据文件名、内容相似或上传次序自动生成 `V001/V002` 资料版本链。内容哈希一致只说明重复接入；只有上传方明确声明或资料中存在可靠的版本号、生效时间或替代声明时，才登记资料间的替代关系。
- 对同一份原件重新运行解析能力只形成新的处理运行和解析结果，不把解析器或模型更换误写成资料版本。
- 单份资料可以立即完成解析。当本次处理只要求资料解析时，在 `DocumentPackage` 可用后结束；当本次处理要求构建销售知识时，在 `DocumentPackage` 可用后自动进入销售知识识别，不能根据尚未产生的知识域或模块命中结果决定是否启动识别。
- 资料级知识域只能作为处理路由提示，不能把整份资料排他性归入单一 D1—D5 知识域。
- 当本次处理要求构建销售知识时，销售知识识别是必经阶段，由大模型参与语义识别并受 STKB 销售知识模型规则约束，负责从全文 Markdown 中识别、提取并按业务对象边界聚合 0～N 个候选知识，同时识别每个候选知识的主域、主模块、对象类型和来源证据，可附带实体提及、引用角色建议与待判定实体/对象关系。该过程不是对全文的机械切分；D1—D5 和22个模块用于识别、分类和规则约束，不作为逐项模型调用拓扑。
- 大模型按受约束 JSON 返回候选知识传输内容，程序完成结构、枚举值、必填内容和来源定位校验后，才形成运行中的候选知识结构；原始 JSON 串不作为正式候选对象、数据库记录或长期知识文件。
- 实体提及只是原文中的名称或描述，不是正式 `BusinessEntity`。候选进入知识归并前必须按工作区、实体类型、可靠外部业务标识、规范名称、别名和上下文完成实体归一，形成复用已有实体、建议新增实体身份或异常结果；待新增身份只有在引用它的知识处理结果被接受时才正式登记，无法可靠归一时不建立正式实体或对象—实体引用。
- 实体类型集合由当前销售知识模型约束，实体实例集合允许随新资料增长。实体归一程序读取关系型数据库中的已有实体和本批其他归一结果；归并前可以使用正式实体 ID 或批内临时实体标识，待新增实体不提前正式落库。
- `KnowledgeObject` 与 `BusinessEntity` 不靠 content 字符串长期绑定。正式绑定必须保存稳定对象身份、稳定实体身份、引用角色和来源证据；实体改名或新增别名不应要求重建知识对象身份。
- 文档片段是从全文 Markdown 中按标题、页码、表格或时间标记派生的证据定位；技术实现可以按需选取局部上下文，但不建立“抽取窗口”业务对象或必存内容层。
- 同一段证据可以支撑多项、多域知识，但候选拆分依据是业务对象边界，不是原文自然段、命中模块数、句子数、字段数或表格单元格数。
- 候选知识是对“新建、更新或补充某项知识”的临时提议，不是另一类长期知识对象。
- 候选知识只在本次识别、实体归一和归并运行中存在，不默认在内部文件系统按候选数量生成长期文件；只保留驱动正式变化的处理动作、目标对象和必要原因。
- 候选形成不是通用文本抽取：系统需要依据当前有效的 STKB 销售知识模型，判断什么内容构成销售训练知识、属于什么知识域和对象类型、应如何聚合为业务对象以及可能建立哪些关系。

### 2.3 自动判定与发布边界

- 系统自动判定和发布是默认路径，人工仅处理明确冲突、信息不足或无法安全决定的异常项。
- 自动校验至少覆盖基本类型、主要内容、来源证据、显式冲突和关键适用条件；具体量化阈值可以通过技术验证确定，但不能因阈值未定而省略这些校验责任。
- 模型可以理解和提出候选，但正式发布不应只依赖模型的单次输出或一个置信度分数。
- 各阶段必须同时说明“负责能力”和“主要执行方”：大模型参与销售知识语义识别和必要的归并判断；程序代码负责路由、编排、校验、状态、规则执行、正式写入和发布控制；外部技术栈负责解析、模型推理以及文件、关系、向量和图谱的物理存储。大模型不能直接写入正式知识文件或关系型登记，人工不作为默认执行方。
- 业务实体归一与知识归并是连续但不同的动作：前者确认“资料里说的是谁”，输出已有实体 ID、待新增实体身份提议或异常；后者确认“候选是不是同一项知识、应当去哪里”，输出忽略、补证、新增、更新、退出或异常等知识处理结果。两者可以由同一流程服务连续执行，但必须有独立规则、结果和异常原因。
- 实体归一的实现是程序与大模型分工：程序读取候选结构、销售知识模型、已有实体登记和原文上下文，优先执行外部业务标识、规范名称、别名和必要实体关系匹配，并管理批内临时实体标识；大模型只对程序缩小后的少量可能实体进行语义消歧，不直接查询实体库、分配正式实体 ID 或写入数据库。
- 知识归并的实现是程序与大模型分工：程序使用实体归一结果，按工作区、对象类型、实体身份、适用范围和类型化身份缩小范围，向量只辅助召回可能相同的对象；大模型只对小范围候选做必要的语义身份判断；最后由程序执行硬规则校验和最终动作。大模型不直接写入正式存储。

### 2.4 知识形态与检索

- 文件、向量和图谱不是地位相同的三种投影：正式知识文件保存 `KnowledgeObject` 规范正文；向量索引和知识图谱是围绕正式知识构建的检索结构。
- 文件形态需要区分来源证据目录和正式知识目录：前者一份资料一份 `full.md`，后者一个当前 `KnowledgeObject` 一份 Markdown；正式知识文件不是全文 Markdown 的简单复制，也不是多个对象拼成的主题文章。
- 向量只负责发现语义相近的候选内容，不单独决定相同、更新或冲突。
- 图谱负责表达已确认关系、支持跨域查询和影响分析，不单独决定知识身份。
- 文件内容必须按访问方式分开落存：所有格式的原始文件，以及图片、音视频、复杂图表和附件等二进制随文资源进入对象存储；内部文件系统默认只长期保留每份资料的 `full.md` 和每个当前 `KnowledgeObject` 的正式 Markdown；正式 `BusinessEntity`、`KnowledgeObject` 身份与修订登记、文件路径与校验值、对象—实体引用、实体关系和对象关系进入关系型数据库；候选知识、完整模型原始输出和报告文件不作为默认长期文件层；知识构建结果与索引构建结果进入关系型处理账本；向量和图谱进入各自物理空间。
- 关系型数据库保存各类内容的业务身份、版本和稳定定位：内部文本使用文件系统命名空间与相对路径，对象内容使用对象存储命名空间与 object key。数据库和 Markdown 都不把临时签名 URL 当长期地址；知识页通过逻辑资源引用关联原件和二进制资源，由 STKB 鉴权后返回文件流或短期地址。
- Agent 默认直接访问当前工作区的正式知识目录，使用 `list/glob/grep/read` 发现一对象一份的当前知识文件；系统通过关系型登记中的对象路径、校验值和正式知识修订点确认当前完整状态，不要求在知识目录额外长期保存一份 manifest，也不让 Agent 扫描对象存储 bucket。

## 3. 已确认的方案修正

### 3.1 主流程修正

当前讨论默认采用以下逻辑链：

```text
知识工作区内的原始资料
→ 资料接入、原件落存及来源登记
→ 能力包路由
→ 正文/表格提取和必要随文资源落存
→ 全文 Markdown 组装与落存
→ DocumentPackage 可用
→ 销售知识识别，大模型输出受约束候选 JSON
→ 程序解析、校验为带实体提及和引用角色建议的候选知识结构
→ 业务实体归一：读取实体规则和已有实体，形成正式实体 ID、批内临时实体标识或异常
→ 销售知识归并判定：确认候选是不是同一项知识、应当去哪里
→ 形成忽略、补证、新增、更新、退出或异常等处理结果
→ 对接受的处理结果，形成或更新正式业务实体、知识对象、对象—实体引用、实体关系和对象关系
→ 一对象一份写入正式 Markdown 知识文件，并登记对象身份、版本、路径和校验值
→ 记录本次知识构建结果
→ 从同一正式知识修订点构建向量检索索引和知识图谱
→ 切换当前发布版本
```

这是一条最终能力链，不是每份资料必须同步执行到底的单次任务链。主链按“资料解析、文档级知识识别、正式知识形成、索引与图谱发布”四个阶段门槛推进；资料解析以原件和必要随文资源可定位、全文 Markdown 可用且资源引用可读取为完成条件。

“销售知识识别”“业务实体归一”和“销售知识归并判定”都由当前有效的 STKB 销售知识模型约束。识别负责提出对象边界、类型、归属、实体提及、引用角色建议以及待判定实体/对象关系；实体归一负责把提及解析为已有实体、待新增实体身份或异常，但不立即把每个待新增身份写成正式实体；知识归并负责判断是否为同一知识以及如何归并、更新或保留异常。只有被接受的知识处理结果才触发正式实体、知识和引用的一致写入。不能把销售领域机制省略成通用抽取后的相似度比较，也不能把22个模块变成22轮抽取。

### 3.2 `KnowledgeObject` 当前语义

- `KnowledgeObject` 是 STKB 基于自身“知识域—知识内容模块—知识对象”业务框架提出的本地逻辑概念，不是照搬 GraphRAG、LlamaIndex、OpenViking 或 WeKnora 的同名对象。
- 它指“可以独立识别、归并、更新和使用的一项业务知识”；D1、D3、D4 三个真实样例已验证稳定知识身份的必要性。重点对象类型的逻辑内容与身份合同必须在方案确认前补齐，最终物理字段和序列化 Schema 不在方案层冻结。
- `KnowledgeObject` 的业务身份不由一句话、字段、表格单元格、Markdown 段落、文件名、向量 chunk 或图节点决定；但当前物理合同明确一个生效对象对应一份当前 Markdown 知识文件。
- 同一对象可以包含多个共享业务身份、适用范围和生命周期的字段、清单条目、流程步骤、表达变体或案例事件。独立更新不等于每个字段必须独立成对象；只有身份、适用范围、生命周期、复用方式、关系端点或消费方明显独立时才拆分。
- 候选和正式对象数量不能由原型中的既有拆分结果预设。对象粒度需要同时接受“业务可用性”和“批量处理成本”验证。
- 本方案不冻结其最终字段名、front matter、序列化 Schema 和物理表结构，但已确定规范正文保存为一对象一份当前 Markdown，身份、版本、路径、校验值、实体引用和关系在关系型数据库登记。

### 3.3 知识构建结果与检索构建记录

- 不再保留 `KnowledgeAssetPackage` 作为核心业务对象。它此前混合了本批处理结果、正式知识集合、投影输入和发布协调四种职责，导致额外的身份、版本和成员生命周期。
- 一批 `DocumentPackage` 完成实体归一和知识归并后形成或更新正式知识文件和结构化登记，同时形成不可变的知识构建结果，记录构建运行、输入文档包、正式知识修订点，以及本次新增、更新、补证、复用、退出、忽略和异常的实体、知识对象与关系引用。
- 知识构建结果只有构建运行 ID，不拥有独立业务 ID、业务版本、成员生命周期或发布状态；任务执行状态仍由处理任务记录承担。
- 向量索引和知识图谱读取同一正式知识修订点下的知识文件与结构化登记。知识构建结果中的变化引用只提供增量影响范围提示，不能成为知识正文或关系来源。
- 向量索引和知识图谱分别保存构建记录，包括正式知识修订点、构建范围、目标物理空间、合同版本、状态和结果引用；当前发布绑定同一修订点下的正式知识文件登记和成功构建记录。

### 3.4 过度设计修正

- 当前不将 `CandidateKnowledgeSet`、`Knowledge Resolver`、`KnowledgeObject Registry`、`Candidate Index` 和 `KnowledgeChangeSet` 作为五个独立架构组件。
- 候选集合、销售知识识别、归并判定、正式知识集合、并发去重和发布差异等职责需要保留，但先作为处理产物、核心能力或内部实现问题，不在当前总体方案中各自建模成独立系统组件。
- 删除独立的 `Knowledge Resolver` 名称不等于删除领域理解能力；其职责由“销售知识识别、业务实体归一、销售知识归并判定”三个连续动作承接，并由同一套销售知识模型约束，但不因此要求部署三个独立组件。
- 不再引入 `KnowledgeBlock` 作为文件层中间对象；一个当前 `KnowledgeObject` 直接对应一份当前知识文件。`RetrievalUnit` 只作为向量或混合检索的派生单元，不与核心领域概念并列。

### 3.5 STKB 销售知识模型

- “STKB 销售知识模型”是定义 STKB 如何理解、组织和治理销售训练知识的可演进业务模型。D1—D5 和知识内容模块是它的当前组成，但不等于它的全部内容。
- 它至少需要表达：哪些知识类型属于哪些销售知识域和知识内容模块；每类知识的业务含义与对象边界；业务实体类型、实体归一和对象—实体引用角色；判断同一知识、补充、更新和冲突所使用的类型化规则；允许建立的实体关系和对象关系；最低限度的适用范围、证据和安全使用约束。
- 它更接近“领域模型加治理规则”，不能只称为普通配置。普通配置通常只改变运行参数，而销售知识模型的变化可能改变候选拆分、知识归属、对象身份和历史知识解释，因此需要版本、生效边界和必要的重分类或迁移机制。
- 它不等于 AI 应用提示词、陪练场景配置或运行状态，也不要求当前立即设计成数据库表、规则引擎或某种配置文件；当前先确认业务语义和变化机制。
- 当变化只涉及知识域或模块归属时，原则上不应因此新建另一项 `KnowledgeObject`，而是对同一知识重新分类；当对象类型定义或身份规则发生变化时，才需要重新判定受影响知识是否拆分、合并或迁移。
- 当前 D1—D5 和现有 22 个知识内容模块直接作为方案分类基线。未来是仅扩展模块和对象类型，还是调整顶层知识域，暂不预设；变化需要经过销售知识模型变更评审和生效边界管理，而不是将当前分类硬编码为不可变结构。

### 3.6 知识工作区与行业知识分发

- 0731 内部讨论中用于描述数据隔离的正式概念是“工作区”。当前至少区分平台维护的行业知识工作区和客户独有的企业知识工作区。
- 企业上传的资料、由此形成的 `DocumentPackage`、企业实体、知识对象、正式关系、知识构建结果、正式知识文件、向量索引和知识图谱都属于该企业工作区。当前关系型数据的多租户隔离采用一个客户一个独立数据库；文件、向量和图谱存储分别使用各自技术栈支持的目录、前缀、集合、命名空间或独立数据库完成物理映射。
- 工作区是业务和逻辑边界，不等同于某个 `dbname`、文件目录或向量 collection；物理隔离方式可以随技术栈变化，但不能改变工作区的知识归属和访问边界。
- 行业知识由行业知识工作区统一维护，并单向分发给企业工作区使用。企业不能直接修改行业原知识，但可以在自己的工作区创建企业扩展或覆盖知识；企业知识优先，行业知识作为补充。
- 为适配一个客户一个数据库的隔离方式，行业知识可以物理复制或投影到企业数据库，但必须保留其行业工作区来源、知识对象身份和版本联系，避免复制后变成无法同步、无法追溯的新事实。

### 3.7 新资料、明确替代、处理状态与质量结果

- 新上传资料不默认视为原资料的新版本。当且仅当上传方或可靠证据明确该资料替代某份已有资料时，两个独立 `DocumentPackage` 之间才登记替代关系；新资料仍重新经过解析、销售知识识别和对象级归并，不直接覆盖已有 `KnowledgeObject`。
- 当前主链已经包含正式知识“退出”结果，因此方案确认前必须说明来源撤回、知识退出、旧知识文件版本和旧索引回收，以及共享证据仍被其他知识引用时的处理边界；具体删除 API、数据库级联和存储回收任务留到实现设计。
- 资料处理任务只保留“初始化、进行中、已完成、失败”四种简单状态。重试、降级和质量问题是处理动作或结果，不扩展为大量任务状态。
- 无法生成可用 `DocumentPackage`、能力调用无输出或输出无法支持基本证据定位时，任务判定失败。部分内容可用时可以判定已完成并记录质量问题；是否命中 D1—D5 销售知识属于后续抽取结果，不决定解析任务成败。
- “输出过少”不能只按字符数判断，需要结合原资料页数、可读区域、表格或音视频时长以及关键内容覆盖判断。具体阈值和工具级规则留到能力包验证阶段，不在当前架构讨论中冻结。

### 3.8 正式文件、向量和图谱的发布一致性

- 正式知识文件和关系型登记共同形成正式知识修订点；向量索引与知识图谱从该修订点读取内容和关系，并共同引用 `KnowledgeObject`、`BusinessEntity` 和正式关系版本。
- 关系型登记中的当前正式知识文件集合、向量索引和知识图谱均通过校验后再切换当前发布版本；任一步骤失败时继续保留上一可用版本，不让部分新结果与旧结果混合成为当前版本。
- 向量或图谱构建失败不反向修改正式知识对象；系统依据失败记录中的正式知识修订点、影响范围和合同重试，并将每次构建结果作为独立记录保留用于追溯。
- 具体如何实现原子切换、物理双写、索引别名或版本指针属于后续技术设计，当前只确认上述一致性语义。

### 3.9 业务图模型与知识图谱边界

- 完整方案必须完成当前 D1—D5 和 22 个知识内容模块到知识对象类型、业务实体类型、对象—实体引用角色、实体关系、对象关系及映射规则的业务语义梳理；20 个计划建设模块需要完整覆盖，2 个可选模块需要明确标记其可选状态和预留边界。
- “业务图模型”是 `STKB 销售知识模型` 的组成部分，不是图数据库内部的技术 Schema。它约束销售知识识别、实体归一、对象拆分、对象—实体引用、实体关系、对象关系判定、跨域检索和知识图谱构建；知识图谱只负责把关系型登记中已确认的知识对象、业务实体和正式关系物化为可查询结构。
- 每类知识对象至少需要说明业务含义、所属知识域与知识内容模块、对象身份和拆分边界、可能引用的业务实体类型与引用角色、允许建立的实体关系和对象关系及方向、资料到对象和关系的映射规则、产生环节、明确消费方和适用资料。没有来源依据或消费方的实体、引用角色、实体关系、对象关系和字段不进入当前模型。
- 知识对象与业务实体必须保持区分：知识对象表达可独立识别、归并、更新和复用的一项事实、方法、策略、话术、案例或评估知识；业务实体表达可被多个知识对象共同引用的产品、版本、客户特征、场景、阶段等稳定业务对象或上下文。两者通过稳定 ID、有类型引用角色和证据正式绑定，不依赖 content 字符串匹配。
- 当前总体方案中“22 个知识内容模块的完整对象类型登记”和“全量关系编码和图谱本体”不再整体延期。方案确认前需要完成当前业务范围内的对象类型登记、核心关系字典和覆盖矩阵；未来销售知识域、未来模块和当前没有业务消费方的扩展关系可以不纳入本次范围。
- 图数据库选型、节点和边的物理字段、Label、主键、索引、查询语言、物理隔离、性能与容量设计留到技术验证和实现阶段，不属于业务图模型的冻结内容。
- 当前五个知识域和 22 个知识内容模块的对象、实体、关系、来源及消费方映射见 [STKB D1—D5 知识对象与业务图模型映射矩阵](./STKB-D1-D5知识对象与业务图模型映射矩阵.md)。该矩阵仍需用真实样本校验，不代表物理图谱 Schema 已冻结。

### 3.10 方案完整性与技术验证边界

- 方案必须在进入技术验证前完成相关环节的逻辑闭环，包括输入、输出、对象身份、存储职责、关系语义、失败边界和最低验收；技术验证用于检验方案假设，不负责替方案补齐缺失的核心设计。
- 第一阶段先验证不同类型资料能否按“原件落存与登记 → 必要随文资源落存 → 全文 Markdown 组装与落存”的顺序稳定形成 `DocumentPackage`；这一阶段不以形成候选、正式知识、向量索引或知识图谱为验收条件。
- 第二阶段选择少量全文 Markdown 验证文档级综合识别、调用成本、候选聚合和对象粒度；不按22个模块循环，不把已有原型对象数量当作标准答案。
- 第三阶段只选择对象边界已通过评审的重点类型，验证一对象一份正式知识文件、关系型登记、知识构建结果记录及向量/图谱检索结构；不要求一次覆盖全部模块和全部存储技术。
- 药享保 PDF 是可复用的样本之一，不再作为整个验证工作的名称、唯一样本或覆盖边界；D2 及其他不足部分需要适合的补充资料。
- 各阶段验证用于检验产物是否可生成、可衔接、可追溯和可消费，不等同于启动全量开发，也不以一次验证结果直接冻结生产技术方案。
- 验证发现的新问题需要区分为方案缺陷、实现选项和未来扩展。方案缺陷必须明确回写并重新评审，不能由实现代码静默改变已经确认的业务语义。
- 代表性资料可以在方案收敛过程中作为设计证据使用；对应环节的逻辑合同明确并经业务与技术联合评审后，才启动技术实现验证和正式开发。

### 3.11 文档片段与正式知识文件的边界

- 解析和标准化阶段先形成原件存储引用和按需产生的随文资源，再组装 `DocumentPackage` 的解析主交付“全文 Markdown”。按章节、页码、表格位置或时间段定位的局部证据称为“文档片段”，它是全文 Markdown 的派生定位视图，不是第二份内容主存。
- 销售知识识别默认以全文 Markdown 进行一次文档级综合识别；需要局部上下文时可以临时选取文档片段，但不建立“抽取窗口”业务对象，也不要求持久化一套片段文件或数据库记录。
- 文档级识别形成候选知识；候选知识经过文档内聚合和归并判定后才形成或更新正式 `KnowledgeObject`。
- 正式对象形成后直接写成一对象一份的当前 Markdown 知识文件，不再额外经过 `KnowledgeBlock` 编排层。解析阶段的普通文档切片也不得命名为知识对象或正式知识文件。
- 正式知识文件按对象主域和主模块放置；跨域复用与主题关联通过对象 ID 和正式关系表达，不复制出多份正文。

### 3.12 知识域与知识内容模块的边界

- 知识域按销售训练中的业务职责划分知识，回答某项知识主要服务于“卖什么、卖给谁、怎么卖、具体怎么说、如何评价”中的哪一个问题。知识域数量少、变化成本高，是跨企业和应用保持稳定的顶层分类。
- 知识内容模块是知识域下的治理分组，用于组织一组业务含义、对象身份规则、治理方式和消费路径相近的知识对象类型。它不是实际知识、业务实体、物理数据库或文件目录。
- 知识域和知识内容模块用于候选与正式对象的分类、类型合同选择、导航和覆盖检查，不表示模型需要按域或模块逐项执行。
- 知识对象是被识别、归并、更新和使用的实际知识单元；每个对象设置一个主归属域和主归属模块，跨域复用通过对象关系表达，不通过复制或多重主归属解决。
- 当前方案直接按现有五个知识域和 22 个知识内容模块的职责完成知识对象、业务实体、关系和资料映射规则梳理，不在本轮重新评价模块数量和命名。后续如需调整，作为销售知识模型的新版本单独评审和生效。

## 4. 真实样例验证记录

### 4.1 D1 产品事实（已完成首例验证）

已使用药享保真实绩优话术中的“单次赔付上限 200 元”，与现有尊享版 300 元、全能版 500 元产品事实进行端到端比较，确认：

- 同一来源行可以支撑一个或多个临时知识提议；是否拆分需要依据知识身份、适用范围、更新生命周期、复用方式和消费方判断，既不能把整行强制合成一个对象，也不能按每个字段机械拆成对象。
- D1 先按事实主题、产品或版本上下文、适用范围和更新生命周期判断对象边界；归一化后的字段值和单位用于对象内部比较和冲突定位，不自动决定对象数量。来源权威等级、版本和生效时间用于决定如何处置，不属于知识身份本身。
- 相同业务键出现不同数值时，不能仅凭语义相似度判为版本变化。版本变化还需要明确版本号、生效日期、新版正式资料或替代声明等证据。
- 低权威经验材料与已有产品事实冲突，且没有新版依据时，系统可以自动不采纳其事实提议，同时保留相反证据和原始案例；不需要默认进入人工审核。
- `KnowledgeObject` 在 D1 中具有初步成立的治理价值：它为一项可独立更新的产品事实提供稳定身份，用于承接当前有效内容、适用范围、证据和冲突；它仍不等同于 Markdown、向量 chunk 或图节点。
- 发布差异只需先表达为一次处理结果中的操作清单，不恢复独立的 `KnowledgeChangeSet` 架构组件。
- 文件视图保留规范事实和可追溯证据，向量视图区分正式事实与含错误的案例表达，图谱视图表达案例与事实的冲突关系；三者不各自决定事实真值。
- D1、D3、D4 样例证明需要追溯同批知识变化，并协调正式知识文件、向量索引和知识图谱，但不证明需要独立知识资产包。当前将其拆为不可变知识构建结果、正式知识修订点和独立索引构建记录，具体语义以 3.3 节为准。

本例使用的 300/500 元口径已由当前可访问的产品宣传页交叉支持，但候选表引用的 B 级正式产品说明原文件位于未挂载目录，本轮没有完成原文件复核；该限制不影响本次架构边界判断，但不能替代后续正式产品事实核验。

### 4.2 D3 方法与策略（已完成首例验证）

已使用药享保质检标准、标准话术和第二轮组合训练资料，对“画像特征切入”与“年轻线上购药客户的药享保切入策略”进行端到端比较，确认：

- D5 中“人群特征切入是否命中”的检测标签、D3 中描述如何切入的技巧、D3 中带有触发条件和推荐动作的场景策略是三个不同知识对象，不能因名称相近而归并。
- 方法或技巧的知识身份需要包含适用范围、方法目标和作用机制；策略的知识身份需要包含产品或方案范围、触发条件和推荐动作。场景、阶段和限制仅在确实影响策略行为且有来源支撑时加入。
- 单一产品资料只能证明产品范围内的方法，不能通过删除产品语境自动提升为企业级通用技巧。本例中的“画像特征切入”暂应收窄为药享保销售中的产品级技巧。
- 具体策略在方法基础上增加产品、客户触发条件和推荐动作，应保持独立并通过“应用了”关系连接技巧，不直接合并。本例同时使用画像特征切入和生活化场景切入，“实例化了”关系过强，暂不采用。
- 质检表中的检测标签只能作为 D5 评价依据，不能单独证明 D3 方法内容；D3 方法需要引用真正描述实施方式或提供稳定示例的资料。
- 候选策略中没有来源支撑的禁用动作、限制或推断内容不能由模型静默补齐；应删除或显式引用其他合规、方法或产品事实。
- 系统可以根据证据覆盖自动收窄适用范围、修正来源和建立关系，不需要默认人工审核。只有要将产品方法提升为跨产品通用方法时，才需要更多产品或通用方法证据。
- 当前关系字典尚未明确“策略应用技巧”和“评价项评价技巧”的关系语义；先记录语义缺口，不在 D4 完成前扩展关系编码或冻结 Schema。

### 4.3 D4 异议与话术（已完成首例验证）

已使用药享保标准话术、候选知识表和真实成交对话，对“我有医保、不用这个”及其实际表达进行端到端比较，确认：

- 客户异议、应对话术和真实对话案例是三个不同知识对象：异议表达客户顾虑或拒绝原因，应对话术表达如何回应，真实案例保留原始轮次、结果和上下文；三者不能因出现在同一行或同一对话中而合并。
- “我有医保、不用这个”和“买药可以走医保，没必要到网上购买”针对同一产品决策，具有相同根本顾虑和处理方向，应归入同一异议对象；后者作为表达变体和来源证据，不新建异议对象。
- 话术的可复用变体与来源证据必须区分。含义、应对方法和适用范围相同且满足基本事实、表达约束的不同说法，可以作为同一话术对象的发布变体；含未核验事实、版本限定、绝对化表达或过程噪声的真实原话，只作为案例证据，不直接进入默认可复用话术。
- 即使处理同一异议，应对目标、方法或适用条件明显不同的话术仍应独立管理。例如解释医保互补价值、比较已有同类商业保障、接受客户明确取消，是不同处理行为，不能只因客户都提到“已有保障”而归并。
- 同一客户表达同时包含“已有医保”“已有同类商业保障”和“明确取消”时，应让同一段证据关联多个已有异议对象，而不是机械创建组合异议对象；“明确取消”还应受到低压沟通或合规边界约束。
- 异议身份主要依据目标产品或购买决策、根本顾虑、客户意图和所需处理方向；话术身份主要依据所处理异议、回答目标、应对方法、引用事实和适用范围。语气、长短和措辞通常不构成独立身份。
- 候选表当前把完整回答同时放入异议对象和独立话术对象，造成职责混合和内容重复。正式设计应把异议的规范含义与处理它的话术分开，并通过“话术处理异议”关系连接。
- 系统可以自动归并明显同义的异议表达，并将明显不宜复用的真实原话限制为案例证据；只有根本顾虑难以判断，或引用事实、适用版本无法由现有 D1 与约束规则确定时，才需要异常确认，不设置默认逐条人工审核。
- 正式知识文件分别保存异议、可复用话术和真实案例对象；向量索引分别生成检索单元，并限制风险原话进入默认生成范围；知识图谱表达话术处理异议、话术引用产品事实、话术应用销售方法、话术受合规规则约束以及案例提供证据等关系。
- D4 进一步证明 `KnowledgeObject` 不是一组相似文本，而是一项具有稳定业务身份的知识；一个对象可以拥有规范表达、多个证据和若干可发布变体。当前 Markdown 文件承载该对象的规范正文，向量切片和图节点只是检索表达。

## 5. 已放弃或暂缓的方向

- 不把一份来源文件或一次批次固化为知识对象边界。单文件或批量接入都只形成对应知识构建结果，结果边界不反向决定知识对象粒度。
- 不把一份资料排他性归入一个销售知识域。
- 不以人工逐条审核作为默认发布路径。
- 不让向量或图谱分别维护一套知识正文，也不让它们独立决定归并和冲突；正式知识正文以当前 Markdown 文件保存，身份和关系以关系型登记为准。
- 本方案不冻结 `KnowledgeObject` 的最终 front matter、数据库表或图节点 Schema；但必须定义重点类型的逻辑内容与身份合同，并且已经明确原件和二进制随文资源进入对象存储，`full.md` 与正式知识文件进入内部文件系统，对象身份、版本、文件定位、实体与正式关系进入关系型数据库，向量和图谱作为派生检索结构。
- 不把候选集、归并器、注册表、候选索引和变更集各自设计为当前必需的独立架构组件。
- 本方案不冻结具体产品、表名、字段、索引和部署拓扑，也不因此提前进入全面实现验证；这不意味着可以省略各类内容本体、事实主存和定位记录的物理分工。
