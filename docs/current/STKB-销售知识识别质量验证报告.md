# STKB 销售知识识别质量验证报告

## 1. 验证结论

本轮验证不再以“模型返回了 JSON”或“页面展示了候选对象”作为完成标准，而是同时检查：

- 对象是否符合 22 个知识模块的内容合同；
- 正文是否足以承载可复用的业务知识，而非只有几十字 summary；
- 每个核心字段是否能回溯到原子主张和来源锚点；
- 模型遗漏、臆造或无法安全归类的内容是否被显式拒绝或记为未决；
- 候选对象是否真正形成具有稳定 ID、修订号、源追溯和 Markdown 正式文件的 `KnowledgeObject`。

四类真实资料的 Gold 分组要求均已命中，证据支撑率为 100%，summary-only 对象为 0。这证明当前机制已从“流程演示”进入“有基准、有门禁、有追溯、能形成正式对象”的可调试阶段。但 Gold 仍是代理评审初稿，不等同于业务人已确认。

## 2. 验收门禁

| 维度 | 判断方式 |
| --- | --- |
| 预期对象组 | Gold 按业务语义定义最小/最大数量、必需证据、内容字段和禁止类型 |
| 内容完整性 | 22 个模块各自定义必填字段、列表项结构、最小正文量和身份线索 |
| 事实与归因 | `claimUsage` 必须指向真实、非空且承载业务知识的 content 路径 |
| 遗漏处理 | 每个可用来源锚点都必须进入对象、拒绝项或未决项，不允许静默丢失 |
| 错误输出 | 不支持的触发条件、动作、话术、事实引用要删除或拒绝，不以“模型说了”作为证据 |
| 正式化 | 质量通过的候选对象生成稳定 `KnowledgeObject ID`、修订、源追溯和正式 Markdown |

## 5. 本轮发现与调优

1. **合同过于简略**：将 22 个模块从“模块代码+一句说明”提升为按对象类型定义的内容 Schema、列表项字段、身份线索、最小信息量和正反例指导，版本为 `object-content-contracts-v1.3`。
2. **“一个 summary 就是知识”**：引入结构合同和 summary-only 检测，要求维度带允许值、策略带条件/决策/动作、流程带步骤、术语带定义和适用语境等。
3. **模型会把同一资料过度合并或错分模块**：增加编码枚举维度、明示术语、完整话术、稳定规则和对话分支的确定性守卫。
4. **模型会补写未出现的动作或话术**：按原子主张重建可核验动作；只说“按照范本”但没有范本正文时，不生成完整话术对象。
5. **主张和来源锚点会被静默丢失**：增加对象内字段级 `claimUsage`、运行级主张核算和来源锚点核算。
6. **数量验收太僵硬**：Gold 允许按组定义有界或无上界的可接受区间。例如合规资料可因合理拆分产生 13–20 个独立检查点，验收重点是必需证据和内容完整性，而非逼迫模型每次返回同一数量。

## 6. 版本与可复现性

- Prompt：`sales-identification-v0.12`
- 模型输出 Schema：`candidate-knowledge-object-v0.7`
- 销售域/模块目录：`d1-d5-v0.7`
- 对象内容合同：`object-content-contracts-v1.3`
- Gold：每份资料目录下的 `gold-v0.1.json`
- 运行证据：PostgreSQL 运行记录和 `workspace/runs/`本地快照；正式知识文件位于 `workspace/knowledge/`。

外部方法与工具调研见 `docs/research/STKB-销售知识对象抽取质量调研.md`。本轮主要借鉴了文档级关系抽取的“证据句与对象标签分开评估”、生成式抽取的“粒度/事实性/完整性分维评估”、以及证据归因的可恢复性思路；没有直接照搬外部英文数据集、实体关系集或评分阈值。

## 7. 边界与后续优先级

- Gold 当前状态为 `proxy_draft`：由 Codex 代理人工角色起草和调试，后续需用户对模块归属、对象边界和必需证据做业务确认。
- 真实模型输出存在随机性，已通过确定性守卫和 Gold 评估收敛，但不能用一次通过代替持续回归。
- 药享保资料仍需人工判断 22 项跨资料等价关系；这是当前最应优先在 Web 审阅页完成的业务验收。
- 本报告验证了正式 Markdown 知识文件和运行/对象数据持久化；pgvector 和 Neo4j 投影不是本轮销售识别质量的验收主体，不将其表述为已完成质量联调。
