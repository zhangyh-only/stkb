# STKB 通用销售知识规则体系与识别机制重审建议

> 状态：评审稿，不代表规则体系已完成重构，也不授权直接改造代码。

## 先看这一部分

STKB 要做的事情可以概括成一句话：**把不同资料中的销售知识整理成可重复使用的知识对象，建立它们之间的联系，再按助手、陪练等 AI 应用的当前任务取出需要的组合。**

### STKB 保存什么

STKB 保存五类内容：

1. 产品、服务和方案的事实；
2. 客户画像、需求和决策信息；
3. 销售场景、方法、策略和合规要求；
4. 客户问题、异议、回应话术和案例；
5. 训练评价和知识回归标准。

原始资料、一次对话状态、一次评分结果和模型运行日志不属于销售知识。它们分别作为来源证据或运行记录保存。

### 六个词分别是什么意思

| 名称 | 通俗理解 | 例子 |
| --- | --- | --- |
| 知识域 | 销售知识的大类 | 产品与事实、客户与决策 |
| 知识内容模块 | 一组一起管理、更新和使用的知识 | 供给事实与价值、回应与对话内容 |
| KnowledgeObject | 真正保存和检索的一条知识 | “企业版支持自动对账，但只支持指定账单格式” |
| `objectType` | 这条知识使用哪套字段模板，不是新层级 | 产品事实使用“主体、事实、适用范围、限制”模板 |
| 关系 | 一条知识与其他知识为什么有关 | 某产品能力满足某项需求，某话术受到某项合规规则约束 |
| KnowledgePackage | 某次 AI 任务实际取出的知识组合 | 为一次角色扮演取出画像、需求、产品、异议、话术和评价规则 |

结构只有三层：

```text
知识域
  └─ 知识内容模块
       └─ KnowledgeObject

KnowledgeObject = 通用字段 + 按 objectType 选择的字段模板
KnowledgeObject ←关系→ KnowledgeObject
```

### 五个域和十二个候选模块

| 域 | 回答的问题 | 候选模块 | 常见内容 |
| --- | --- | --- | --- |
| D1 供给与事实 | 卖什么，事实和使用规则是什么 | 供给事实与价值；供给规则与履约流程 | 产品能力、价格、清单、价值、办理和交付流程 |
| D2 买方与决策 | 卖给谁，客户为什么行动 | 买方模型与决策角色；需求、动机与行为信号 | 画像、角色、需求、痛点、动机和可观察信号 |
| D3 销售行动与约束 | 在什么场景下应该怎么做 | 销售场景与旅程；销售方法与策略；销售约束与合规 | 阶段、方法、策略、下一步动作和禁限要求 |
| D4 互动与内容 | 客户怎么表达，销售怎么回应 | 客户表达与交互意图；回应与对话内容；案例与赋能资产 | 问题、异议、回答、话术、案例和销售卡片 |
| D5 评价与治理 | 怎样判断做得好不好 | 评价模型与评分规则；基准与回归治理 | 能力维度、评分规则、Gold 和回归检查 |

12 个模块是当前评审候选，不是为了替换原来的 22 个模块而新定一个硬数量。跨行业样本验证后仍可合并、拆分或改名。

### 一个完整例子

假设某企业协作产品资料中说明：系统支持自动核对账单，但只支持指定格式。客户访谈又表明，财务人员希望减少人工核对时间。

STKB 不把这些内容写成一篇摘要，而是保存为几条能够独立更新的知识：

| 知识对象 | 保存的内容 | 与其他知识的联系 |
| --- | --- | --- |
| 产品事实 | 支持自动核对账单；仅支持指定格式 | 支撑产品价值和回应话术 |
| 客户需求 | 希望减少人工核对时间 | 被产品价值和销售策略处理 |
| 产品价值 | 自动对账可以减少重复核对 | 由产品事实支撑，针对该客户需求 |
| 销售策略 | 先确认账单格式，再演示自动核对 | 适用于该需求，受产品限制约束 |
| 回应话术 | 说明支持范围，并请客户提供样例验证 | 采用该策略，引用产品事实 |
| 评价规则 | 是否确认格式、是否准确说明限制 | 用于评价策略和话术执行 |

它们之间形成下面的关系：

```text
产品事实 ─支撑→ 产品价值 ─解决→ 客户需求
   │                              │
   └────────被引用────────┐       └─适用→ 销售策略
                          ↓                 │
销售约束 ─约束→ 回应话术 ←指导──────────────┘
                  ↑
评价规则 ───────检查销售策略和回应话术
```

因此，AI 可以从任意一点开始检索：从产品找适用话术，从客户需求找产品和策略，从话术回查事实依据，也可以从评价规则找到它要检查的行为。

### 不同 AI 应用怎样使用

| 应用 | 通常从哪里开始 | STKB 返回什么 |
| --- | --- | --- |
| 知识问答 | 用户问题或产品名称 | 事实、规则、限制和来源证据 |
| 对话分析 | 客户的一段表达 | 意图、需求、信号、相关策略和评价依据 |
| 销售建议 | 客户需求、画像和销售阶段 | 推荐动作、理由、事实、话术和合规限制 |
| 角色扮演 | 场景、角色和产品 | 角色信息、需求、异议、可见事实和回应空间 |
| 训练评价 | 对话记录和评价任务 | 评价维度、评分规则、证据要求和改进引用 |
| 场景包 | 一个训练或业务场景 | 锁定版本的产品、画像、策略、话术、合规和评价组合 |

知识只维护一份。应用名称不写进每条知识；STKB 在收到具体任务时再检索和组装。

### 当前实现需要改变什么

1. 把偏保险、互相重叠的 22 个模块改成跨行业候选结构，并用样本确认最终数量。
2. 保留 `objectType` 作为 KnowledgeObject 的字段模板选择，不把它展示成知识层级。
3. 把对象关系正式保存下来，使产品、画像、需求、策略、话术和评价可以互相查找。
4. 将标准文档的模型调用目标从几十次降到 2—4 次；只有超长文档或质量失败时追加调用。
5. 正式 Markdown 使用标题、段落、表格和列表；JSON 只作为可选机器文件。
6. Web 先展示处理流程，再按需展开每次模型调用的输入、输出、token、耗时和结果去向。

### 这轮需要重点判断什么

快速评审只需要判断四件事：

1. 五个域是否覆盖了通用销售知识；
2. 十二个模块是否存在明显重复、遗漏或名称不准确；
3. 上述完整例子是否符合 STKB 预期的知识拆分和关联方式；
4. 助手、陪练等应用是否能从这些关系中取到需要的知识。

## 1. 结论先行

本轮需要纠正此前过度收缩的方向：**不取消销售域，也不取消知识内容模块。**

STKB 面向多个 AI 应用提供统一的销售知识检索与装配。域和知识内容模块承担稳定分类、治理、导航和检索过滤；KnowledgeObject 是实际管理和检索的知识；每个对象通过 `objectType` 选择内容与身份合同；对象关系负责跨模块连接。`objectType` 不是新的目录或业务层级。

建议采用以下分层：

```text
销售域 Domain
  └─ 知识内容模块 KnowledgeModule
       └─ 知识对象 KnowledgeObject

KnowledgeObject ──按 objectType 校验──> 对象内容合同
业务实体 BusinessEntity ──────────────┐
类型化关系 TypedRelationship ─────────┼─ 跨对象和跨模块连接
检索视图 RetrievalProfile/View ───────┤
KnowledgePackage ──────────────────────┘ 运行时装配结果
```

当前 5 域可以保留编码，重新定义行业中立语义。初审曾把 22 个模块压缩为 10 个；本轮逐项对照内容合同、身份合同、生命周期和消费者后，建议改为 **12 个评审候选模块**。增加的两个边界分别是“销售场景与旅程 / 销售方法与策略”和“客户表达与意图 / 回应与对话内容”。12 仍是待样本验证的候选数量，不是新的硬编码。

真正比模块数量更关键的缺口是：当前关系只存在于候选生成阶段，没有进入正式 KnowledgeObject、正式文件、数据库和检索接口；代码中也尚未形成可供助手与陪练调用的 KnowledgePackage 合同。因此现状并不能支持产品到话术、画像、策略、合规、评价之间的正向或反向多跳检索。

## 2. 事实、判断与待验证目标

### 2.1 当前实现事实

1. `catalog.py` 将 5 域、22 模块设为强校验条件；模块不是展示标签。
2. 内容合同、身份合同、Prompt、确定性 guard、覆盖检查、对象生成分组、正式文件路径和运行 lineage 都以模块为分派键。
3. 正式对象身份由 `objectType + identityKey` 主导，数据库唯一约束不含域和模块。这为分类迁移时保持对象身份提供了可能，但需要验证内容指纹和文件路径变化的影响。
4. 候选对象允许生成自由文本 `relationType`，代码主要校验端点是否悬空；正式 KnowledgeObject 没有关系字段，数据库也没有正式关系表。
5. 当前仓库没有完整的 pgvector、Neo4j 检索能力和 KnowledgePackage API 实现。已有文档描述的是目标合同，不是已跑通能力。
6. `_render_markdown()` 把 `content` 写成 JSON fenced block，因此文件扩展名虽为 Markdown，正文仍不是面向人的知识表达。
7. 当前识别链路按发现分段、规划批次、覆盖修复、模块与对象类型分桶生成，因此一个文档会产生几十次模型调用。

### 2.2 外部通用方法提供的边界

W3C SKOS 将概念体系中的上下位关系与关联关系分开；OWL 把类、实例和对象属性分开；SHACL 用独立 Shape 约束数据图。这些规范共同说明：分类导航、对象内容合同和跨对象关系是不同职责，不应为了减少模块而压成一层。[SKOS](https://www.w3.org/TR/skos-reference/)、[OWL 2 Primer](https://www.w3.org/TR/owl-primer/)、[SHACL](https://www.w3.org/TR/shacl/)

Microsoft GraphRAG 区分基于实体与关系的局部检索和基于社区报告的全局检索；Neo4j GraphRAG 同时提供向量、混合检索和检索后图遍历。这说明应用查询需要按任务选择检索策略，而不是让一个固定目录直接承担所有应用行为。[Microsoft GraphRAG](https://microsoft.github.io/graphrag/query/overview/)、[Neo4j GraphRAG](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)

这些是结构边界参考，不直接证明 STKB 应有 5 域或固定模块数；具体数量仍要由本地资料、消费任务和回归结果决定。

### 2.3 本轮设计判断

1. 保留 Domain 和 KnowledgeModule 两层。
2. Domain 是稳定业务视角；Module 是内容治理、对象路由和检索过滤单元；KnowledgeObject 是知识主体，`objectType` 只是对象采用的合同标识，不构成第三层目录。
3. 将 22 个模块显著合并，避免把主题、对象类型、流程阶段、交付形态混用为同级模块。
4. 关系必须成为正式、一等、可追溯对象，能够跨模块、跨对象类型和跨修订连接。
5. 应用侧通过 RetrievalProfile 和 KnowledgePackage 使用知识；不为助手、陪练分别复制知识。

### 2.4 待验证目标

- 12 个候选模块能否无歧义覆盖通用销售资料，而不会把模块做成大杂烩。
- 产品、画像、需求、策略、话术、合规、评价之间能否用少量受控关系表达，而不是无限增长关系类型。
- 同一知识对象能否被问答、对话分析、角色扮演、评价和场景包装配复用。
- 标准单文档是否能把真实模型调用降到 2—4 次，同时维持证据覆盖和对象质量。
- 新 Markdown 是否同时满足人读、机器重建和版本追溯。

## 3. 五个销售域的行业中立定义

| 域 | 建议语义 | 解决的问题 | 主要消费 | 不负责 |
| --- | --- | --- | --- | --- |
| D1 供给与事实 | 卖什么、事实是什么、价值如何成立、如何交付 | 知识问答、推荐依据、话术事实支撑 | 助手、陪练、推荐、合规校验 | 客户决策解释、销售动作选择 |
| D2 买方与决策 | 谁购买、为什么购买、如何识别需求与信号 | 客户识别、需求判断、角色与动机建模 | 对话分析、角色扮演、策略选择 | 产品事实、销售表达成品 |
| D3 销售行动与约束 | 在何种场景采取什么方法、策略和约束 | 下一步行动、销售策略、流程与合规控制 | 助手、教练、场景编排 | 具体话术文本、评价结果 |
| D4 互动与内容 | 如何表达、问答、处理异议，以及用什么案例或物料支持 | 对话生成、异议应对、案例与内容检索 | 聊天助手、角色扮演、销售赋能 | 底层产品真值、评价规则 |
| D5 评价与治理 | 如何检测、评分、比较和做回归 | 训练评价、对话分析、知识质量回归 | 评估器、运营、知识治理 | 销售策略本身、营销卖点 |

域是相对稳定的检索与治理视角，不要求知识只在域内使用。一个 D1 产品事实可以通过关系被 D4 话术、D3 策略和 D5 评价共同消费。

| 候选模块 | 主要承接的当前模块 | 核心职责 | 为什么单独存在 | 不负责 |
| --- | --- | --- | --- | --- |
| D1.1 供给事实与价值 | D1.1、D1.2、D1.4、D5.1 的卖点 | 产品/方案事实、清单、对比快照、价值主张 | 都以可核验供给为主体，价值必须回指事实 | 业务办理流程、销售动作、营销口号 |
| D1.2 供给规则与履约流程 | D1.3 | 资格、价格、使用规则及交付/服务流程 | 规则和流程共同约束供给如何被获得和履行 | 销售会话策略、销售合规检查 |
| D2.1 买方模型与决策角色 | D2.1、D2.2、D2.5 | 画像维度、买方画像、决策角色和影响关系 | 描述相对稳定的买方结构，可跨单次会话复用 | 当前客户状态、一次行为推断 |
| D2.2 需求、动机与行为信号 | D2.3、D2.4 | 需求、痛点、动机、顾虑及可观察信号 | 回答客户为什么行动，以及有哪些证据可以支持判断 | 具体话术、销售动作、无证据心理推断 |
| D3.1 销售场景与旅程 | D3.1 | 场景、阶段、进入/转移/完成条件 | 生命周期是稳定流程骨架，运行时只引用它 | 某次会话当前阶段、条件化销售动作 |
| D3.2 销售方法与策略 | D3.2、D3.3 | 通用方法、条件化策略、判断规则和下一步动作 | 都为销售行为提供指导，但用对象类型区分通用方法和情境策略 | 场景骨架、完整表达文本、产品事实 |
| D3.3 销售约束与合规 | D3.4 | 必须、禁止、授权边界、风险模式和合规替代做法 | 具有独立权威来源、风险等级和生效周期 | 一般业务规则、未经依据确认的经验禁忌 |
| D4.1 客户表达与交互意图 | D4.2、D4.3 的问题/问法部分 | 问题、异议、意图及表达变体 | 规范化“客户说了什么/想解决什么”，作为检索起点 | 心理根因定论、完整回应、事实答案 |
| D4.2 回应与对话内容 | D4.1、D4.3 的答案/解释部分 | 标准回答、话术、解释、回应结构和表达变体 | 规范化“销售如何回应”，需要引用事实、策略和合规 | 原始对话、未经核验生成稿、客户意图本身 |
| D4.3 案例与赋能资产 | D4.4、D4.5 | 案例事件链，以及引用正式知识的物料/话术卡/微课 | 都是复合内容；通过引用复用原子知识，不复制真值 | 把单案例自动升格为规则、把原始文件当知识对象 |
| D5.1 评价模型与评分规则 | D5.1 的检测部分、D5.2、D5.3 | 能力维度、行为锚点、观察规则、评分和宽容边界 | 共同组成可执行评价合同，运行分数不进入知识 | 产品价值主张、单次评价结果 |
| D5.2 基准与回归治理 | D5.4 | Gold、基准案例、回归探针和验收清单 | 验证对象、合同和模型版本，生命周期不同于业务评价规则 | 未经评审的生产运行记录 |

从 10 调整到 12 的依据不是名称差异，而是独立接口：场景旅程由编排和阶段检测消费，方法策略由建议与训练消费；客户表达由识别和检索消费，回应内容由生成和展示消费。二者若强行合并，模块接口会要求调用方同时理解两套身份和生命周期，形成浅模块。

### 4.1 十二个候选模块的完整审计矩阵

## 5. 多 AI 应用如何消费同一知识底座

### 5.1 典型消费路径

| 应用任务 | 起点 | 关系扩展 | KnowledgePackage 重点 |
| --- | --- | --- | --- |
| 助手知识问答 | 查询意图、产品或业务实体 | 事实 → 规则/流程 → 证据 → 合规 | 直接答案、依据、适用范围、限制与来源 |
| 对话分析 | 对话片段与行为信号 | 信号 → 需求/画像 → 策略/话术 → 评价维度 | 识别结论、证据片段、建议和置信边界 |
| 销售建议 | 客户需求、阶段与产品 | 需求 → 价值/事实 → 策略 → 表达 → 合规 | 推荐动作、话术支撑、禁止项和解释 |
| 陪练角色扮演 | 场景、角色、客户画像 | 画像/角色 → 需求/信号/异议 → 产品边界/案例 | 角色状态、可用事实、异议路径和动态触发 |
| 陪练评估 | 评价模型与会话证据 | 维度 → 观测点 → 评分规则 → 事实/策略/合规 | 分数、证据、扣分原因、改进建议 |
| 场景包 | 场景或业务目标 | 产品 → 画像/角色 → 需求/信号 → 策略/话术 → 合规/评价/案例 | 同一修订点上的可执行知识集合 |

这些路径不是硬编码链条。它们是 RetrievalProfile 的默认策略，运行时仍应基于查询、上下文、权限范围、修订和 token 预算裁剪。

### 5.2 为什么不能把应用名称写进知识对象

知识对象描述的是稳定业务知识；应用名称和具体任务变化更快。同一个产品限制既可能服务问答，也可能限制角色扮演，还可能成为评价扣分依据。若把应用用途固化到对象身份或必填字段中，会造成复制、版本分叉和召回遗漏。

更合理的边界是：

- KnowledgeObject 保存稳定语义、范围、证据、状态和关系。
- RetrievalRequest 声明本次用途、上下文、知识需求、锚点、约束和预算。
- RetrievalProfile 定义某类任务默认采用哪些检索通道、关系方向、跳数和重排规则。
- KnowledgePackage 返回本次经过解释和裁剪的对象、关系路径与证据。

## 6. 对象、实体与关系合同

### 6.1 KnowledgeObject 通用字段

| 字段 | 定义与存在理由 | 生产者 / 消费者 | 身份 | 证据 | 推导与可空性 | 与相似字段的区别 |
| --- | --- | --- | --- | --- | --- | --- |
| `knowledgeObjectId` | 一项正式知识跨文件、登记和投影的稳定引用 | 正式登记生成；全部应用消费 | 是；稳定 ID | 不需要原文证据 | 确定性生成；不可空 | 不等于运行内 `candidateId` |
| `revision` | 同一对象规范内容的一次不可变修订 | 正式登记生成；检索、审计、场景包消费 | 是；修订身份 | 不需要原文证据 | 递增/派生；不可空 | 不等于来源文档版本或 catalog 版本 |
| `catalogVersion` | 指明对象按哪一版域、模块和类型合同形成 | 正式化器写入；迁移、校验消费 | 否 | 不需要 | 由规则包决定；不可空 | 不改变业务对象身份，只影响分类和合同解释 |
| `domain` | 对象所属的稳定顶层业务职责 | 识别建议、规则/人工确认；治理和检索消费 | 否 | 分类理由需引用内容 | 可从 module 校验但不应单独猜测；不可空 | 不是来源目录、应用用途或数据库分区 |
| `module` | 一组身份、治理和消费路径相近的对象类型 | 识别建议、规则/人工确认；Prompt、检索、治理消费 | 否 | 分类理由需引用内容 | 不能仅从关键词推导；不可空 | 不是 ObjectType，也不是物理子库 |
| `objectType` | KnowledgeObject 采用哪一份对象边界、内容 Shape 和身份字段合同 | 识别建议、合同校验确认；正式化和消费者使用 | 是；参与身份算法 | 合同选择需内容证据 | 不可从 module 唯一推导；不可空 | 是对象属性，不是模块下的导航层 |
| `identityKey` | 对类型身份字段规范化后的可比较业务键 | 确定性身份规则生成；归并和修订消费 | 是 | 依赖身份字段证据 | 可推导；不可空 | 不是标题、内容 hash 或文件路径 |
| `title` | 让人能区分对象的简短名称 | 模型建议、正式化校验；阅读和搜索消费 | 否 | 应能由内容支持 | 可重写；不可空 | 不参与同一对象判断，不能替代 identityKey |
| `content` | 符合 ObjectType Shape 的规范业务内容 | 模型抽取、规则归一、人工修订；应用和投影消费 | 内容中的指定字段参与身份 | 事实性字段逐字段绑定证据 | 不可整体为空；子字段按 Shape | 不保存运行解释、检索分数或应用输出 |
| `scope` | 行业、企业、地区、渠道、买方、供给项和有效时间等适用边界 | 来源抽取、实体归一、人工确认；过滤和冲突处理消费 | 部分类型参与身份 | 显式范围需证据；缺失时标未知 | 可部分为空，但不能用空表示全局适用 | 不等于访问权限，也不等于 entityRefs |
| `entityRefs` | 指向已归一业务实体并说明引用角色 | 实体归一产生；图检索、过滤和影响分析消费 | 部分引用参与身份 | 每个引用保留提及证据 | 无相关实体时可空 | scope 说明适用边界；entityRefs 说明具体指向谁 |
| `evidenceBindings` | 把内容字段或关系主张映射到 DocumentPackage 定位 | 识别链路产生、人工可修订；引用、审核、回归消费 | 否 | 本字段本身就是证据合同 | 原始抽取对象不可空 | 不只保存文档 ID，必须定位到支持哪个字段 |
| `status` | 对象是否待审、有效、冲突、废止 | 登记和治理产生；检索过滤消费 | 否 | 状态变化需治理记录 | 不可空 | 不等于构建运行成功/失败状态 |
| `relationshipRefs` | 引用正式 TypedRelationship，便于文件阅读和影响分析 | 关系登记生成；图检索、场景装配消费 | 否 | 关系实体保存自己的证据 | 无已确认关系时可空 | 不在 content 中复制关系两端和关系真值 |
| `provenance` | 记录来源资料、构建运行、规则/模型和人工活动 | 构建与治理链路产生；审计和重建消费 | 否 | 记录生成活动，不证明业务主张 | 不可空 | evidence 证明内容；provenance 说明内容怎样形成 |

通用字段只解决对象级合同。类型字段还必须说明业务含义、身份参与、证据要求和可空条件，不能再用 `required_fields + minimum_content_chars` 代替语义。

### 6.2 BusinessEntity 的作用

BusinessEntity 是产品、客户组织、角色、场景、渠道等稳定上下文锚点，不等同于 KnowledgeObject。知识对象是关于实体的可版本化陈述。例如产品是实体，产品能力、适用条件和价格规则是不同知识对象；多个知识对象可以共同指向同一产品。

### 6.3 TypedRelationship 最小合同

| 字段 | 语义 |
| --- | --- |
| `relationshipId` | 稳定关系 ID |
| `relationType` | 受控关系注册表中的类型 |
| `sourceRef` / `targetRef` | 两端对象或实体的 ID 与修订 |
| `direction` / `inverseLabel` | 显式方向与反向读取语义 |
| `scope` / `effectivePeriod` | 关系适用范围与有效期 |
| `evidence` / `ruleId` | 来源证据或确定性生成规则 |
| `status` / `provenance` | 确认状态与生成过程 |

首批只验证八种关系，不一次冻结旧设计中的全部关系名：

| 关系 | 允许的起点 → 终点 | 反向读取 | 为什么需要 | 证据要求 |
| --- | --- | --- | --- | --- |
| `ABOUT` | 任一知识对象 → BusinessEntity | `HAS_KNOWLEDGE` | 说明知识具体关于哪个产品、角色、场景等实体 | 对象—实体提及和归一证据 |
| `APPLIES_TO` | 规则/方法/策略/回应/评价 → 供给、画像、场景或阶段实体 | `HAS_APPLICABLE_KNOWLEDGE` | 支持范围过滤和场景装配 | 来源明确适用范围；未知不得当全局 |
| `SUPPORTS` | 事实集/案例 → 价值主张、方法、策略、回应或评价规则 | `SUPPORTED_BY` | 防止卖点、话术和评分脱离依据 | 支撑字段及来源定位；不能只靠向量相似 |
| `ADDRESSES` | 供给价值/策略/回应 → 需求或交互意图 | `ADDRESSED_BY` | 从需求、异议或问题找到可用供给与动作 | 来源明确或人工确认的业务对应关系 |
| `GUIDES` | 方法/策略 → 场景、阶段或回应 | `GUIDED_BY` | 从场景找方法，从话术回到策略原因 | 方法步骤或策略判断与目标对象的对应证据 |
| `CONSTRAINED_BY` | 流程/策略/回应/资产 → 业务规则或销售约束 | `CONSTRAINS` | 在生成、角色扮演和评价中带回限制 | 正式规则依据及适用范围 |
| `EVALUATED_BY` | 方法/策略/回应/场景 → 评价模型或评价规则 | `EVALUATES` | 从知识找到如何观察和评分，也支持反向覆盖分析 | 评价目标和对象行为的明确映射 |
| `EXEMPLIFIED_BY` | 事实/需求/方法/策略/回应 → 案例或赋能资产 | `EXEMPLIFIES` | 获取示例或教学内容而不把案例当通用真值 | 案例事件或资产引用指向的具体知识 |

`DERIVED_FROM`、`GENERATED_BY` 等属于 provenance，不放入业务关系注册表。`SAME_AS`、`REPLACES` 属于身份与版本治理，只有实体归一或修订链确认后使用，也不交给识别模型自由生成。

### 6.4 对象合同字段语义矩阵

下表中的 R 表示业务上必需，O 表示满足条件时填写，I 表示参与 `identityKey`，E 表示必须有字段级来源证据。`scope`、`entityRefs`、`evidenceBindings` 等通用字段不在每种类型中重复。

#### D1 供给与事实

| 对象合同标识 | 内容字段及定义 | 身份字段 | 证据与可空性 |
| --- | --- | --- | --- |
| `OFFERING_FACT_SET` | `subjectRef`：供给实体；`factTheme`：共同更新的事实主题；`facts`：名称、值、单位、条件组成的事实项；`limitations`：该主题自身的限制 | `subjectRef + factTheme + scope.effectivePeriod` | 前三项 R/E；`limitations` O/E，来源未说明限制时为空，不写“无限制” |
| `REFERENCE_LIST` | `listName`：清单业务名称；`subjectRef`：适用供给实体；`versionLabel`：来源定义的清单版本；`itemSchema`：成员业务键和字段含义；`items`：成员及纳入/排除条件；`membershipRules`：集合级资格规则 | `listName + subjectRef + versionLabel + scope` | 除 `membershipRules` 外 R/E；成员很多不构成拆对象理由 |
| `VALUE_PROPOSITION` | `subjectRef`：价值来自哪个供给；`customerValue`：给买方带来的结果；`targetNeedRefs`：对应需求；`supportingFactRefs`：支撑事实；`qualification`：价值成立条件；`expressionHints`：可选表达要点 | `subjectRef + customerValue + targetNeedRefs + scope` | 前五项 R；`customerValue`、`qualification` E，引用关系各自有证据；`expressionHints` O，不作为标准话术 |
| `COMPARISON_SNAPSHOT` | `subjectRefs`：被比较供给；`dimensionSet`：同口径维度；`observations`：逐维度事实与来源；`effectiveAt`：快照时点；`comparabilityNotes`：口径差异 | `subjectRefs + dimensionSet + effectiveAt` | 前四项 R/E；`comparabilityNotes` O/E；不允许用主观优劣替代 observations |
| `BUSINESS_RULE` | `subjectRef`：规则约束的供给或业务；`rulePurpose`：规则解决的问题；`conditions`：何时适用；`requirements`：必须满足的业务要求；`exceptions`：例外；`outcomes`：满足或不满足的结果；`basisRefs`：权威依据 | `subjectRef + rulePurpose + scope + effectivePeriod` | `subjectRef`、`rulePurpose`、`requirements` R/E；其余按来源 O/E；未写条件不能补造 |
| `FULFILLMENT_PROCESS` | `subjectRef`：办理/交付主体；`processGoal`：完成的业务结果；`participants`：参与角色；`entryConditions`：进入条件；`steps`：有序动作、责任方和转移；`completionCriteria`：完成边界；`exceptions`：异常路径 | `subjectRef + processGoal + scope` | `processGoal`、`steps`、`completionCriteria` R/E；其他 O/E；单个步骤默认不是对象 |

#### D2 买方与决策

| 对象合同标识 | 内容字段及定义 | 身份字段 | 证据与可空性 |
| --- | --- | --- | --- |
| `PROFILE_DIMENSION` | `dimensionName`：稳定名称；`businessMeaning`：区分买方的业务含义；`valueSet`：值代码和定义；`usageBoundary`：允许用于哪些判断、不能推出什么 | `dimensionName + businessMeaning + scope` | 全部 R/E；某客户当前取值不进入该对象 |
| `BUYER_PROFILE` | `profileName`：人读名称；`stableTraits`：跨样本稳定特征；`decisionPattern`：有证据的决策方式；`concerns`：持续关注点；`behaviorBoundary`：允许概括的反应边界；`exclusionSignals`：不应归为该画像的证据 | `stableTraits + decisionPattern + scope` | 前五项 R/E；`exclusionSignals` O/E；人口属性不足以单独形成画像 |
| `DECISION_ROLE` | `roleName`：角色类型；`decisionContext`：家庭或组织决策情境；`authority`：决策权责；`concerns`：稳定关注点；`influenceRelations`：与其他角色的影响关系 | `roleName + decisionContext + scope` | 前四项 R/E；`influenceRelations` O/E；个人姓名不是角色身份 |
| `CUSTOMER_NEED` | `subjectType`：需求主体类型；`needTheme`：规范需求主题；`problem`：待解决问题；`desiredOutcome`：期望结果；`context`：需求出现的业务情境；`observableEvidence`：可观察支持；`urgencyIndicators`：紧迫性证据；`expressionVariants`：常见表述 | `subjectType + needTheme + context + scope` | 前六项 R/E；紧迫性和表达 O/E；卖点不能反向充当需求证据 |
| `BEHAVIOR_SIGNAL` | `signalName`：规范信号；`observablePattern`：可直接观察的表达/行为模式；`context`：观察语境；`supportedInterpretations`：来源支持的可能含义；`nonInferenceBoundary`：禁止推出的结论；`evidenceScope`：支持稳定性的样本边界 | `observablePattern + context + scope` | 全部 R/E；单次反应只能保留为案例证据，不能形成已确认信号规则 |

#### D3 销售行动与约束

| 对象合同标识 | 内容字段及定义 | 身份字段 | 证据与可空性 |
| --- | --- | --- | --- |
| `SALES_SCENARIO` | `scenarioName`：稳定场景名称；`businessGoal`：场景完成目标；`participantRoles`：参与角色；`entryConditions`：进入条件；`stages`：阶段名称、目标和完成标志；`transitions`：阶段转移条件；`completionCriteria`：整体完成边界 | `scenarioName + businessGoal + participantRoles + scope` | 全部 R/E；运行时当前阶段不写回对象 |
| `SALES_METHOD` | `methodName`：方法名称；`purpose`：解决的销售问题；`mechanism`：为什么有效；`steps`：有序方法动作；`applicabilityConditions`：适用条件；`nonApplicabilityConditions`：不应使用的情况 | `purpose + mechanism + core steps` | 前五项 R/E；不适用条件 O/E；资料只给名称和口号时不形成对象 |
| `SALES_STRATEGY` | `strategyName`：人读名称；`strategyGoal`：行动目标；`triggerConditions`：触发情境；`decisionLogic`：条件到判断的规则；`actions`：建议动作；`stopConditions`：停止、切换或升级条件；`clarifyingQuestions`：补足判断信息的问题 | `strategyGoal + triggerConditions + decisionLogic + scope` | 前五项 R/E；停止条件和澄清问题按来源 O/E；完整话术另建 D4.2 对象 |
| `SALES_CONSTRAINT` | `ruleName`：约束名称；`modality`：必须/禁止/限制；`constrainedBehavior`：受约束行为；`basis`：法规、制度或授权依据；`riskConsequence`：违规影响；`compliantAlternative`：允许做法 | `constrainedBehavior + basis + scope + effectivePeriod` | 前四项 R/E；风险后果和替代做法 O/E；无依据经验不能成为正式约束 |

#### D4 互动与内容

| 对象合同标识 | 内容字段及定义 | 身份字段 | 证据与可空性 |
| --- | --- | --- | --- |
| `INTERACTION_INTENT` | `intentName`：规范意图；`intentKind`：问题/异议/请求/确认等受控值；`context`：发生语境；`expressionVariants`：可观察表达；`linkedNeedRefs`：有证据关联的需求/顾虑；`interpretationBoundary`：不得从表达推出的结论 | `intentName + intentKind + context + scope` | 前四项和边界 R/E；需求引用 O，关系另存证据；不保存完整回应 |
| `RESPONSE_GUIDE` | `communicationGoal`：回应目标；`applicableIntentRefs`：适用意图；`responseStructure`：应覆盖的要点与顺序；`scriptVariants`：可发布表达；`factRefs`：事实依据；`strategyRefs`：采用的方法/策略；`constraintRefs`：合规边界；`forbiddenClaims`：明确不能表达的承诺 | `communicationGoal + responseStructure + applicable intents + scope` | 目标、结构、表达和事实引用 R/E；策略、约束和禁止承诺按场景 O，但高风险场景不得省略合规引用 |
| `SALES_CASE` | `caseContext`：案例背景；`participants`：参与角色；`events`：有序事件与行为；`outcome`：结果；`lessons`：来源明确的经验；`generalizationLimit`：不能外推的范围 | `case identity + participants + time scope` | 全部 R/E；没有结果或只有一句轶事不形成正式案例 |
| `ENABLEMENT_ASSET` | `assetName`：发布单元名称；`assetRef`：原始媒体/文件引用；`deliveryFormat`：展示形态；`contentSummary`：人读摘要；`usagePurpose`：分发目的；`knowledgeRefs`：引用的正式知识及修订 | `assetName + deliveryFormat + scope` | 全部 R；摘要和用途 E，引用必须有效；原始文件内容不复制进对象 |

#### D5 评价与治理

| 对象合同标识 | 内容字段及定义 | 身份字段 | 证据与可空性 |
| --- | --- | --- | --- |
| `EVALUATION_MODEL` | `modelName`：评价模型名称；`evaluationTarget`：被评价能力/行为；`dimensions`：维度定义与权重；`behaviorAnchors`：可观察表现；`proficiencyScale`：等级及分界；`applicableScenarios`：业务适用场景 | `evaluationTarget + dimension set + model version + scope` | 全部 R/E；学员分数和一次会话表现不进入对象 |

| `EVALUATION_BENCHMARK` | `benchmarkName`：基准名称；`validationGoal`：要验证的行为；`targetVersions`：被测 catalog、Prompt、模型或检索版本；`inputs`：稳定输入；`expectedResults`：对象/关系/输出预期；`checks`：可执行检查；`approvalBasis`：人工确认依据 | `validationGoal + targetVersions + benchmark scope` | 全部 R；输入、预期、检查和批准依据需可追溯；未经评审运行结果不能覆盖预期 |

### 6.5 容易混淆的字段边界

| 字段对 | 区别 |
| --- | --- |
| `scope` / `context` | `scope` 是对象正式适用边界；`context` 是需求、信号、意图或策略成立的业务情境。缺少 context 可能使对象无意义，缺少某个 scope 维度只表示该维度未知。 |
| `conditions` / `triggerConditions` / `entryConditions` | 业务规则的 `conditions` 决定规则是否适用；策略的 `triggerConditions` 决定是否采取动作；流程/场景的 `entryConditions` 决定能否进入。不能统一成无语义的 conditions。 |
| `facts` / `factRefs` | `facts` 是本对象负责维护的供给真值；`factRefs` 只是引用 D1 已有事实。话术和价值主张不得复制事实正文。 |
| `limitations` / `SALES_CONSTRAINT` | `limitations` 是供给自身边界，如服务不覆盖某地区；`SALES_CONSTRAINT` 约束销售人员的表达或行为。 |
| `observableEvidence` / `evidenceBindings` | 前者是业务上可用于识别需求或信号的观察特征；后者是当前知识字段来自原始资料的回源定位。 |
| `customerValue` / `desiredOutcome` | `customerValue` 从供给角度说明能带来的结果；`desiredOutcome` 从买方角度说明想达到的结果，二者通过关系匹配，不能合并成一个字段。 |
| `behaviorAnchors` / `criteria` | 行为锚点描述某能力等级的可观察表现；评分 criteria 规定一次评价如何判定。前者属于模型，后者属于规则。 |
| `title` / 各类型 `name` | `title` 是展示标题；类型内名称字段若参与身份，则表达稳定业务名称。修改 title 不应生成新对象。 |

## 7. 检索请求与 KnowledgePackage

### 7.1 RetrievalRequest 建议合同

```yaml
purpose: roleplay | evaluation | qa | dialogue_analysis | sales_advice | scenario_package
query: 用户问题或当前任务
context:
  conversation: 可选对话上下文
  sales_stage: 可选销售阶段
knowledge_needs:
  - facts
  - needs
  - strategy
entity_anchors:
  - type: product
    id: product-001
relation_expansion:
  relation_types: [SATISFIES, HANDLES, CONSTRAINED_BY]
  direction: both
  max_hops: 2
constraints:
  effective_at: 2026-08-28
  status: active
  evidence_required: true
budget:
  max_objects: 20
  max_tokens: 8000
```

`purpose` 只描述本次调用目的，不进入 KnowledgeObject 身份。`knowledge_needs` 表示需要哪些知识职责，`relation_expansion` 控制图扩展，`constraints` 保证适用范围和修订一致。

### 7.2 KnowledgePackage 建议合同

- 请求 ID、RetrievalProfile 版本和知识修订点。
- 命中的 KnowledgeObject ID、revision、domain、module、objectType 和 scope。
- 从锚点到对象的关系路径、扩展原因和方向。
- 面向当前任务组织的人读章节，而不是对象 JSON 的直接堆叠。
- 证据、冲突、未决项和适用性警告。
- 重排分数、裁剪原因、token 预算和检索 trace。

KnowledgePackage 是运行产物，不反向决定正式知识身份，也不作为新的永久模块。

### 7.3 六个默认 RetrievalProfile

| Profile | 初始召回 | 允许的主要关系路径 | 必须返回 | 默认停止条件 |
| --- | --- | --- | --- | --- |
| `qa` | 查询文本命中 D1/D4.1/D4.2，并识别供给实体 | `ABOUT`、`APPLIES_TO`、`SUPPORTS`、`CONSTRAINED_BY` | 答案所需事实、范围、限制和证据 | 两跳；没有证据的生成内容不进入包 |
| `dialogue_analysis` | 对话窗口识别 D4.1 意图和 D2.2 信号 | `ADDRESSED_BY`、`GUIDED_BY`、`EVALUATED_BY`、`CONSTRAINED_BY` | 识别结论、原话证据、候选需求、建议及不确定性 | 不把一次推断写成画像；最多两跳 |
| `sales_advice` | D2.2 需求、D2.1 画像、D3.1 阶段 | `ADDRESSED_BY`、`GUIDED_BY`、`SUPPORTED_BY`、`CONSTRAINED_BY` | 建议动作、理由、事实支撑、可用回应和禁限项 | 没有适用范围或支撑事实时降级为待确认 |
| `roleplay` | 场景、角色、画像和供给实体 | `HAS_APPLICABLE_KNOWLEDGE`、`ADDRESSED_BY`、`EXEMPLIFIED_BY`、`CONSTRAINED_BY` | 角色已知信息、需求/信号、异议空间、产品边界 | 不把销售侧不可见知识暴露给角色；按场景预算截断 |
| `evaluation` | D5.1 模型/规则和本次对话证据 | `EVALUATES`、`SUPPORTED_BY`、`CONSTRAINED_BY` | 规则版本、评分证据、分数依据、严重错误和改进引用 | 找不到证据时标未观察，不按缺失自动扣分 |
| `scenario_package` | 场景和供给实体 | 综合使用上述受控关系 | 锁定修订的对象集合、关系子图、可见性和缺口 | 最多两跳；超预算按必需知识职责裁剪 |

所有 Profile 复用同一条最小流水线：关键词/向量/实体召回 → `scope` 与修订过滤 → 受控关系扩展 → 面向任务重排 → KnowledgePackage 装配。具体应用可以覆盖预算和知识需求，但不能绕过正式状态、适用范围和证据门禁。

### 7.4 KnowledgePackage 不变量

- 每个内容片段都能回到 `knowledgeObjectId + revision`，不能只返回生成摘要。
- 每条扩展结果都说明命中方式或关系路径，关系方向和跳数可见。
- 同一包锁定一个知识修订点；发生冲突时同时返回冲突和裁决状态，不静默拼接。
- 包内应用参数、对话状态和裁剪结果不写回 KnowledgeObject。
- 场景包可以持久化引用和版本锁定，但不复制正式知识正文。

## 8. 当前模型调用为什么膨胀

当前调用次数不是模型 token 上限自然要求，而是编排结构的乘法结果。按代码可以概括为：

```text
总调用 N = S + P + Rcoverage + G + Jrepair + Wretry

S：主张发现分段数
P：候选对象规划批次数
Rcoverage：覆盖修复轮次，最多 2 轮
G：按 module + objectType 分桶后的对象生成批次数
Jrepair：JSON 或结构修复调用
Wretry：网关级重试
```

默认 `document_max_chars = 3500`，主张发现实际分段目标约为其一半，即 1750 字符。药享保样例约 8408 字符，发现阶段就形成 7 个片段；随后规划、覆盖修复和每桶最多 5 个对象的生成继续增加调用，最终真实运行达到 32 次。

`G` 的结构尤其容易放大：同一文档只要识别出多个模块和对象类型组合，即使模型上下文仍有余量，也会为每个分桶单独调用。这属于实现选择，不是模型能力限制。

## 9. 三种调用架构比较

| 方案 | 标准文档目标次数 | 优点 | 风险 | 建议 |
| --- | --- | --- | --- | --- |
| A 单次全文结构化识别 | 1 次，失败时 2 次 | 最低延迟、全局上下文完整 | 输出过大时截断，局部错误需重做全文 | 作为短文档基线 |
| B 全文发现与规划 + 批量生成 | 2—3 次 | 职责清楚，便于阶段质量门禁 | 固定两阶段仍可能对简单文档多调用 | 作为稳定对照组 |
| C 少量自适应调用 | 标准文档 2—4 次，长文按需增加 | 简单文档合并，超长或失败才拆分和定点修复 | 编排与证据合同需更精确 | 推荐优先验证 |

推荐 C 的基本原则：

1. 先做全文或大窗口的联合发现与对象规划，不按 1750 字符机械切片。
2. 批量生成允许异构对象，按预计输出 token 平衡批次，不按 module + objectType 强制分桶。
3. 质量门禁由确定性代码执行；只有失败对象或缺口进入一次定点修复。
4. 超长文档先建立文档级索引和锚点，再对必要区域分块，避免所有阶段重复读取所有片段。
5. 禁止默认一个对象一次或一种类型一次调用。

验收时用同一文档比较 A、B、C，不以单次 Gold 10/10 证明架构合理。至少记录调用次数、prompt/completion token、端到端耗时、重试、对象覆盖、证据完整性、重复率、模块/类型正确性和人工可读性。

## 10. Prompt 与确定性规则的调整边界

模块合并后不能只改 TOML 名称。Prompt 应先声明通用对象边界、类型合同和关系合同，再提供模块导航；模型输出对象建议和关系证据，确定性代码负责 ID、Shape、范围、引用完整性和正式状态。

现有 guard 要逐项分为四类：

1. 通用不变量：证据必须落在来源范围、引用端点必须存在、身份字段不可漂移。
2. 类型合同：某对象类型的必填语义和合并拆分规则。
3. 行业扩展：药品、疾病、投保、核保、理赔、退保等只能进入保险扩展包或样例。
4. 编排补丁：因当前 Prompt 或调用拆分导致的补偿规则，应在新架构实验中证明仍有必要，否则删除。

## 11. Web 运行证据的信息层级

页面应先回答流程发生了什么，再允许查看每次调用，而不是把所有 trace 平铺成密集表格。

1. 文档准备：确定性代码展示文档范围、切分依据和字符数。
2. 全文发现与规划：模型节点展示主张、对象计划和覆盖摘要。
3. 规则门禁与缺口判断：确定性代码展示通过、拒绝、缺口及规则 ID。
4. 批量对象生成：模型节点展示生成对象、字段证据和未决项。
5. 定点修复：仅失败时出现，展示触发原因、修复目标和前后差异。
6. 正式化与文件输出：确定性代码展示 ID、修订、路径和投影状态。

模型节点可展开显示：`callId`、`stageId`、目的、输入范围、格式化 Prompt、原始输入摘要、原始输出、解析结果、prompt/completion token、耗时、`retryOf`、错误和产出流向。阶段节点只展示该阶段产生的主张、计划、对象和失败项摘要。

当前已有 ModelCallTrace 的部分字段可以复用，但必须补齐稳定调用 ID、阶段关联、重试链和结果对象 ID，才能解释某次输出如何流入正式知识。

## 12. 正式知识文件格式

采用 YAML front matter + 类型化人读正文；完整机器结构如确有需要，使用同修订的独立 JSON sidecar。运行 trace 不进入正文。

示例 front matter：

```yaml
knowledge_object_id: ko_product_capability_x1
revision: 3
domain: D1
module: D1.1
object_type: PRODUCT_CAPABILITY
status: active
applies_to:
  product: product_x
sources:
  - document_id: doc_001
    locator: section_2
```

示例正文：

```markdown
# 跨境结算到账提醒

## 能力说明

支持在到账后向指定联系人发送提醒。

## 适用条件

- 已开通结算账户。
- 联系方式通过有效性校验。

## 限制与边界

- 提醒不等于资金到账承诺。
- 到账时间以实际清算结果为准。

## 关联知识

- 满足需求：及时掌握回款状态
- 受约束于：到账时效表达规范
- 可用于话术：回款状态说明

## 来源依据

产品说明第 2 节说明到账后可发送状态提醒。
```

front matter 保存身份、修订、分类、范围和来源索引；正文按 ObjectType 渲染标题、段落、表格和列表。JSON sidecar 与 Markdown 共享对象 ID 和 revision，可用于机器重建，但不能重新成为正文主体。

## 13. 迁移影响

### 13.1 规则、Prompt 与 guard

- 重写域与模块目录，不再强制固定 22 个模块。
- 以 ObjectType Shape 替代仅有 required fields、最小字符数和白名单的薄合同。
- Prompt 从枚举 22 模块改为：任务目的、类型合同、关系合同、证据合同、模块导航。
- 逐项审计保险 guard，迁移为行业扩展或删除编排补丁。

### 13.2 Gold 与评估

现有 Gold 围绕当前模块体系标注，不能直接证明新体系正确。需要保存旧标签，建立旧模块到候选模块和对象合同的迁移映射，再让业务评审者针对通用语义重新确认。

新的 Gold 除对象清单外，还要标注：对象身份、字段证据、关系、适用范围、应合并或应拆分，以及至少一个消费任务的期望 KnowledgePackage。

### 13.3 数据库和已有 KnowledgeObject

- 域和模块变化会影响正式文件路径、内容指纹、lineage、检索过滤和统计。
- 当前数据库唯一约束不含域和模块，若 objectType 与 identityKey 不变，可尝试保持 KnowledgeObject ID；若对象语义或身份合同变化，则必须产生迁移记录，不能静默复用。
- 新增正式关系存储时，关系两端必须引用对象 ID 与修订，且可从正式文件重建。
- 旧对象先只读保留，使用显式 catalog version 区分；不要就地覆盖。

### 13.4 Web

- 模块筛选和对象展示需要支持旧、新 catalog version。
- 增加阶段节点与调用明细两层，不在现有页面继续堆字段。
- 增加关系路径和 KnowledgePackage 预览，才能验证多应用消费，而不只验证抽取。

## 14. 最小验证实验

### 14.1 样本

至少选三类脱敏资料：

1. 当前保险样例，只用于迁移对照。
2. 一个非保险 B2B 产品与销售资料，覆盖组织角色、方案、流程、策略和合规。
3. 一个非保险 B2C 或零售服务资料，覆盖个人画像、需求、异议、话术、案例和评价。

### 14.2 离线人工标注

由至少两名评审者对同一资料独立标注候选模块、KnowledgeObject 边界、采用的对象合同和关系；争议项记录理由，不用当前模型输出反向定义正确答案。

### 14.3 六个端到端消费任务

对问答、对话分析、销售建议、角色扮演、评价和场景包各设计至少一个查询。每个查询从不同入口开始，验证正向、反向和最多两跳关系扩展。

### 14.4 调用架构 A/B/C

使用同一模型、同一文档、同一类型合同和同一 Gold 比较三种架构。标准文档的推荐目标是：正常路径 2—4 次调用；不发生默认逐对象调用；全部模型调用在 Web trace 中可解释。

### 14.5 验收标准

- 模块边界：评审者能说明每个模块为什么存在，并对同一对象取得可接受一致性。
- 对象质量：身份、内容 Shape、证据和范围完整；重复和错误合并可量化。
- 关系质量：关键消费路径可达，关系方向、证据和适用范围正确。
- 检索质量：六类任务返回的 KnowledgePackage 覆盖关键知识，没有明显无关扩展，并能解释路径。
- 调用效率：达到 2—4 次目标或给出超出目标的文档级证据；同时报告 token、耗时和修复率。
- 文件质量：业务人员不阅读 JSON 即可理解正式对象，机器文件能够按同一 ID 与 revision 重建。

## 15. 建议实施顺序与确认点

3. 将 TypedRelationship、RetrievalProfile 和 KnowledgePackage 纳入 STKB 基座核心合同。
4. 用多行业样本和多应用消费任务验证结构。
